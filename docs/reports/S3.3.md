## Types, defaults and preservation

All 22 affected numeric columns are profiled before DDL: 11 money columns become
DECIMAL(14,2), five unit-price columns DECIMAL(14,3), six Qnty/QT columns
DECIMAL(12,3). Cash `amt` columns are integer flags and remain unchanged.
Nullable QT/default semantics remain; item stock and snapshot quantities both
support fractions. Unit rates, catalogue purchase prices and snapshot purchase
prices use a consistent three-place scale. Known fractional detail IDs 9783/11934
and three-decimal rate IDs 4487/2832 are preserved. No meaningful extra precision
or range violations exist. Up preflights every affected column before any ALTER;
real half cents or fourth-decimal rates/quantities are refused, not called noise.

38 columns receive type/default changes. Optional numeric values default to 0,
optional VARCHARs to empty strings. The exact reviewed required-field allowlist
is in the data report; dates, business identities/references and existing required
profile TEXT fields deliberately remain required. No TEXT capacity widening,
DATETIME changes, constraints, CSRF or unrelated JavaScript changes are included.
Every column's final type/null/default metadata and every index are checked
against the original metadata with only these explicit changes allowed.

DDL requires stopped writers, a tested backup and mysql without `--force`.
CREATE/ALTER ROUTINE, EXECUTE, ALTER and SELECT belong to the migration account,
not the runtime user. DDL implicitly commits; an interruption can require backup
recovery. Down conservatively refuses fractional/unsupported new data before all
ALTERs; the real fixture already has legitimate fractional history and therefore
requires its backup for rollback. An integer-only synthetic schema rehearses
positive up/down/up and proves exact original types/defaults restored. MariaDB
and Windows were not run; no claim of those runtime tests is made.

## Exact write policy and form checks

`input_decimal()` implements string-based decimal rounding **half away from zero**
without first converting input to FLOAT: quantities/unit prices to three places,
money/discounts to cents. Invalid ordinary input retains the legacy zero fallback;
out-of-range input returns 400 before writes. Exact decimal-string multiplication
handles products beyond PHP integer capacity without BCMath/Composer. Stock
arithmetic explicitly casts parameters to DECIMAL; header totals subtract the
normalized discount from stored line sums using exact SQL DECIMAL operands.
Computed extension, stock-addition and header-total overflow are checked before
writes. Transaction locks, server-owned prices/amounts and existing query counts
are retained. Existing negative sale returns and purchase absolute quantities/
amounts remain. Cash/payment and item catalogue writes use the same boundaries.

Actual forms on synthetic records verify:

- sale input 1.2345 stores 1.235 and stock 10→8.765; forged prices/amounts ignored;
- removing the line restores 10 exactly; a posted bill delete restores stock once,
  repeated deletion has no second effect; negative sale/return reverses exactly;
- purchase negative input -1.2345 stores absolute 1.235; rate 0.3335 stores 0.334 in
  detail, catalogue and actual stock snapshot; line and bill removal restore stock;
- sale 0.005 discount becomes 0.01 before Total; purchase 3×0.3334 normalizes rate
  to 0.333, extension 1.00, discount 0.01 and total 0.99; client totals are ignored;
- catalogue form 1.2345 sales price →1.235 and stock 10.0005→10.001;
- cash collection/expense -0.005→-0.01;
- quantity range and rounding-overflow inputs and computed product/header overflow
  produce clean 400 and preserve header, stock and details;
- an actual test-only trigger forces strict DECIMAL overflow during detail INSERT,
  after stock UPDATE; the real transaction rolls stock back and inserts no line.
