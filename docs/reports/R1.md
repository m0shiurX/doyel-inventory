# R1 — trusted schema and version visibility

Implemented application version 1.1.0, schema version 1 and package format 1.
Source builds display `development`; the reviewed release builder may supply a
safe build token through `lib/build_metadata.php`. No Git inspection or request
input supplies version metadata.

`lib/backup_schema.php` contains reviewed schema-only constants captured from the
local migrated MySQL 8.4.13 database. It includes 13 InnoDB utf8mb4 tables,
99 ordered columns, 37 indexes, four RESTRICT foreign keys and 22 decimal columns.
Trusted CREATE statements exclude volatile AUTO_INCREMENT next values and contain
no records. Restore imports must execute these constants, never uploaded DDL.

The normalized fingerprint includes table engine/collation/options, every column's
type/order/null/default/extra/charset/collation/generated expression, every index
field/order/prefix/visibility/expression, foreign-key targets/rules, checks and
triggers. It omits database names, next IDs and index cardinality. A foreign key
to another schema remains distinguishable from one targeting the selected schema.
Exact mismatch raises a fixed diagnostic without SQL, credentials or record data.

`About.php` requires the existing administrator contract before querying metadata.
It shows only application/build/package/schema compatibility and a constrained
database engine/version token. The Accounts link is visible only to admins.
The page explains owner-managed migrations and outstanding Windows acceptance.
Both new libraries refuse direct HTTP access. The runtime allowlist includes the
new page and libraries.

Validation on PHP 8.4.27 / MySQL 8.4.13:

- PHP lint passed for both libraries, About and Accounts.
- Local HTTP checks passed: guest redirects to login, ordinary role redirects to
  the dashboard, admin sees version 1.1.0 and schema compatibility; both libraries
  return 404 when requested directly.
- Admin HTML contains no database name, DB password, private paths or SQLSTATE.
- A fresh disposable database created from all 13 trusted CREATE statements
  matched the canonical fingerprint. Changing the database name and next
  AUTO_INCREMENT value preserved it; an extra column, extra index and altered
  column default each failed compatibility. Removing each change restored it.
- Both migrated source schemas matched the constants. The disposable database
  was removed after testing. Fingerprint:
  `5679a6a92976bb29f1465bc7f03f094640aee135cd3061699f240f168a072871`.

HTTP role checks used synthetic test sessions in an isolated loopback server;
they performed no login, password rehash or business writes. Schema tests use a
fresh randomly named disposable database; source databases are read-only.
Private test scripts/session state stay under `/private/tmp/doyel-restore-r1`.
Actual Windows acceptance remains pending.
