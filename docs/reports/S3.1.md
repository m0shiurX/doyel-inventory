## Audit correction and lossless precondition

The initial mandatory ASCII-only preflight stopped: one existing row contains
valid Unicode, so the audit's ASCII-only premise was inaccurate. Counts/IDs only:

```text
canteen_sales.Note non_ascii=1
IDs: [["6390"]]
```

The other 35 text columns contain no non-ASCII rows. Independent read-only checks
confirmed the flagged Note is already valid UTF8 in a utf8mb3 column: 35 bytes,
25 characters, including five Bengali Unicode-block characters. The exact
utf8mb3 → utf8mb4 → utf8mb3 binary roundtrip is equal. Neither text, byte sequences
nor hashes are published. No row contents or private source dump were edited.

The orchestrator explicitly approved preserving this valid existing Unicode by
replacing the overly strict ASCII assumption with an enforced lossless criterion:
original latin1 tables remain ASCII-required; other supported Unicode columns
must survive conversion into the target charset and back into their source
charset with exact stored-byte equality. Unsupported charsets or failed
roundtrips abort before charset DDL. This is preservation, not encoding repair.

## Migration and runbook

Both SQL files are sourceable by the mysql client used in `db-reset.sh`. They
require exactly the 13 expected tables and scan **every** text column before any
charset ALTER. Use mysql **without `--force`**. Stop all writers for the entire
preflight/conversion window. Keep a tested backup: DDL commits implicitly, so
an interrupted ALTER sequence can be partial and requires inspection/recovery,
not a transaction rollback. The temporary migration account needs CREATE ROUTINE, ALTER ROUTINE, EXECUTE,
ALTER and SELECT privileges (migration 001 separately requires its DDL privileges).
Do not grant routine/DDL privileges to the application runtime account. Owner-run
production migration remains separate from runtime DML access.

An aborted call can leave the helper procedure;
rerunning safely replaces that named migration helper before scanning again.

Up sets database default, all 13 table defaults and all 36 text columns to
`utf8mb4_unicode_ci`. Down restores the original database default and ten tables
to `utf8_unicode_ci`, with `canteen_expenses`, `canteen_stock` and
`canteen_stock_detail` restored to `latin1_swedish_ci`. MySQL reports original
`utf8` as `utf8mb3`; MariaDB's alias difference is commented in SQL. SQL floor:
MySQL 8.0 / MariaDB 10.6; actual test server MySQL 8.4.13. MariaDB was not run.

Down supports original three-byte Unicode only when byte-exact representability
is proven. Four-byte Unicode in those tables aborts before all charset ALTERs.
Original latin1 tables conservatively require ASCII in both directions. There
is no claim that down can retain all new Unicode writes: restore the backup if
new writes cannot be represented; never strip/truncate them to force rollback.

The new CLI-only checker refuses nonlocal databases and HTTP, emits text counts
and primary IDs only, validates all schema collations and index key budgets,
and supports private external `--snapshot`/`--compare` files. It deterministically
hashes all rows/columns privately to prove exact preservation, without printing
hashes. It refuses overwrite/symlink snapshot paths. No application route changed.
The three existing harness PDO connections now use utf8mb4; the source import's
intentional `SET NAMES utf8` remains unchanged.

## Original TEXT capacity retained

A metadata review identified MySQL CONVERT's automatic TEXT → MEDIUMTEXT widening
for four original fields: customer address/MemberName, sales Note and user
FullName. Both final migrations explicitly restore TEXT with its original
nullability immediately after conversion, avoiding unrelated final type changes.
An initial same-ALTER CONVERT+MODIFY attempt still widened types on MySQL;
actual metadata demonstrated that restoration needs separate ALTERs.
A pre-DDL target-byte-length guard rejects any value over TEXT's 65535-byte
capacity before any charset ALTER. The checker also asserts these fields remain
TEXT. A targeted down/up rehearsal after this correction again preserves all
13 tables' exact row bytes; comparison against original metadata reports zero
changed column types/nullability. The full page/scenario runs preceded this
narrow capacity correction; no application values changed in the targeted
rehearsal, and suites were not redundantly rerun.
