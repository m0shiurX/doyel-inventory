# R4 — isolated candidate import and validation

Implemented 2026-11-07. The owner-only CLI helper consumes sealed R3 jobs,
preflights the complete bounded gzip/data-only package, creates a random new
candidate, and imports bound string/NULL values using trusted canonical DDL.
No uploaded SQL or schema is executed. All rows, accounts, hashes and history are
preserved; no login, pruning or credential replacement occurs.

The temporary importer has only SELECT, INSERT, CREATE, ALTER, INDEX and REFERENCES
on the exact candidate. Database underscores are escaped in GRANT scope. The
import transaction rolls back on insert or orphan failure; all four canonical
foreign keys, every table digest/count, full schema metadata, next-ID lower bounds
and business inventory are checked before ready. Importer removal precedes ready.
Interrupted creating/importing/validating jobs fail closed and retain evidence;
ready jobs do not import again. No automatic database deletion is implemented.
Errors expose only random references; private diagnostics omit SQL, row values,
passwords and raw exception messages.

`php tools/restore/worker.php --once /absolute/private-owner-config.php` handles
one fixed job while holding the R3 global lease. Configuration is an owner-private
PHP return array outside all web/job roots. Required fields: restore_dir,
web_roots, host=127.0.0.1, port=13306, owner_user, owner_password and
active_database. fixture=true additionally permits port 33084 and importer_host=%;
normal importer_host defaults to 127.0.0.1. Optional runtime_config identifies the
private authoritative runtime PHP config: its checked db_name overrides the
owner file's initial active_database for subsequent restores. Configuration paths
reject symlink parents and compare canonical Windows separator/case keys.

Private `owner/<job>/candidate.json` has closed keys: version, job_id,
candidate_database, candidate_nonce, expected_active_database,
source_package_sha256, created_at, owned, activated, importer_user, importer_host,
importer_revoked and validation_receipt. It stores no importer/owner password.
The validation receipt is the original full R2 read receipt. Candidate identity
is pinned to the active database at job creation; after activation R7 must use
activation recovery evidence to distinguish the retained source from the new
current target, rather than reinterpret the pinned identity. R6 can accept
additional owner config keys; R4 ignores them.

Public `<job>.validation.json` contains backup_asof, app, schema (version,
fingerprint, compatible), row_counts, financial, date_coverage, roles,
customer_balances (count/hash only), comparisons, candidate_ref,
candidate_database, expected_active_database, active_row_counts and
active_counts_asof. Financial/date/role shapes match R2. Active counts come from
one consistent read-only snapshot and are comparison evidence, not an activation
freeze. There are no profiles, credential hashes or row contents in this artifact.
