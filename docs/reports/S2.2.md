## Implementation and intentional changes

- All three pages use the shared bootstrap and prepared queries. Password changes
  require login; user management requires admin and halts before unauthorized
  writes. Displayed names/user fields are escaped; array-shaped inputs fail safely.
- Login verifies the original MySQL-escaped MD5 bytes, checks duplicate usernames
  in `user_id` order, upgrades the verified row by ID and regenerates the session
  ID. Stored canonical username/admin values and the matched user ID enter the
  session. Strong hashes verify directly and rehash when needed.
- Hash upgrade uses a compare-and-set against the verified hash. If a concurrent
  operation wins, the current row is fetched and its current password is verified
  before any session can be created. Password change similarly checks the matched
  old hash when updating one user ID; it never changes both duplicate users.
- Blank passwords are rejected, including the legacy empty-password account.
  New users and changed passwords use secure hashes. The existing user page has
  add/list only: no edit route or new edit interface was invented.
- Ordinary passwords use `PASSWORD_DEFAULT` (bcrypt on this PHP 8.4 runtime).
  NUL-containing or over-72-byte passwords use Argon2id, explicitly approved by
  the orchestrator, to avoid bcrypt rejection/truncation. Unsupported runtimes
  produce a plain configuration message and preserve the old hash. Existing
  bcrypt hashes reject over-72-byte/NUL inputs rather than accepting a truncated
  prefix. The runtime requirement belongs in deployment documentation, not UI
  implementation detail. The host exposes `2y,argon2i,argon2id`; actual Windows
  capability remains a cut-over acceptance check.
- Intentional behavior changes: non-admin user management is blocked; empty new
  passwords cannot be stored; login upgrades old hashes without changing the
  password; password changes are scoped to the authenticated duplicate identity.
  CSRF conversion remains Phase 4; it is not claimed here.
