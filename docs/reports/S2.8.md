## Implementation and preserved behavior

Every owned page bootstraps and requires login before output. Request/database
values are bound, displayed values and form attributes are escaped, numeric
accumulators start at zero, and empty or malformed request values do not produce
PHP diagnostics. Existing titles, report headings, tables, print controls and the
item-ledger search form/JS hooks are retained.

The four product reports each use one aggregate/detail query. Category summaries
remain server-calculated SUMs; ordered detail rows are grouped in PHP without
queries inside rendering loops. Categories use the legacy group-column ordering,
items use ItemName with ItemID tie breaking, and the existing type-name labels,
subtotals and grand totals remain unchanged.

Live closing uses two queries. Its legacy asymmetry is deliberately preserved:
active items determine which categories are shown, but positive-stock detail rows
and final COUNT/SUM values are not filtered by D. Category prices/values still
accumulate in the old ItemName order. Saved closing uses three queries and reads
stored snapshot names, quantities and prices, rather than joining the current
catalogue. Its group/detail order is explicit; the stock-detail surrogate ID from
migration 001 provides deterministic ties.

Item ledger uses at most three queries: item lookup, combined opening sums and
period movements. The opening boundary remains inclusive, preserving legacy
behavior even for movements exactly at the start timestamp. Replacing the invalid
zero-date lower literal with `Date <= start` is equivalent for stored DATETIMEs
and runs under the default modern SQL mode. Period rows retain inclusive BETWEEN
bounds and explicit Date/purchase-first/source-ID order; both real fixture ranges
match the legacy output. No new current-stock reconciliation or accounting formula
was introduced.

## Clock normalization correction

The live closing report displays today's date. The original golden was recorded
on October 27, while this verification runs October 28; the old extractor had
missed that wall-clock heading. The orchestrator authorized a single rule in the
extractor's normalization table: only page `report/closingBalance.php`, only the
exact `Closing Balance Date - dd-Mon-yyyy` line, becomes
`Closing Balance Date - <today>`. Historical text and all saved-snapshot dates
remain literal. A synthetic extraction check proves those boundaries.

Before changing the active golden, both original report-closing text files were
copied privately to `s28/golden-originals/`. Each file received exactly one heading
replacement; a byte comparison after removing that one heading proves every other
byte unchanged. Original/canonical SHA-256 checksums and replacement counts are
recorded privately in `s28/clock-normalization.private.json`.

The frozen PHP 5.6 legacy server was then recaptured for **only** report-closing,
using the same new narrow rule. Both full/month outputs match the canonicalized
golden exactly: **2 same, 0 differ**. The two known legacy mysql deprecations stay
in its private error sidecar. This proves the correction normalizes the clock,
not report data. No legacy source or business data was changed.
