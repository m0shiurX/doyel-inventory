## Implementation and grouped-value decisions

Every route bootstraps and requires login before output. Request and session
values are bound, displayed values/URLs are escaped, array-shaped filter inputs
are ignored safely, and accumulators are numeric. The existing report headings,
columns, form names, date semantics and visible calculation formulas remain.
Rows have explicit ordering corresponding to the legacy group/primary-key order.

N+1 work is replaced with constant query sets:

- Sales/purchase bill reports fetch their user choices, bill headers and all
  matching detail rows in three queries. Detail rows are mapped by bill and retain
  ID order; header totals and printed stored detail rates remain distinct.
- Item/user/supplier/category summaries fetch all grouped quantities once rather
  than querying inside each outer group. Their legacy filters are preserved:
  the supplier report includes all dated detail rows, and the user report uses
  header dates and excludes raw material in its item summaries.
- Cash reports fetch grouped sums and their row details in two queries. Details
  retain primary-key order, while heads retain SQL group order. Member dues use
  one query joining preaggregated sales and collection totals; subtraction stays
  in PHP to preserve the legacy displayed float formatting and NULL-as-zero rule.
- Unposted bills join preaggregated detail totals, then retain the old two-decimal
  rounding. The employee summary groups its amounts once.

The strict GROUP BY conversion does not invent a historical unit rate:

| Legacy grouped report | Printed values and deliberate derivation |
|---|---|
| Item-name sales | ItemName and catalogue SalesPrice are constant because ItemName is unique; SUM(detail Qnty) is grouped by item identity/name/price. |
| Item-name sales by user | Same item constants, grouped additionally by UserName; the separate outer SUM(Amount) retains its original inclusion rule and user order. |
| Supplier-name sales | Catalogue SupplierName, ItemName and SalesPrice are constants per item; quantity is grouped once per supplier/item. |
| Category sales | ItemType, ItemName and catalogue price are constants per item; quantities are grouped once per category/item. |
| Factory/process | Catalogue name/price are constant per item; quantities are grouped after the repaired sales-header date join. |
| Cash heads | SUM(amount) is explicit; the printed head spelling comes from the minimum matching PaymentID row, preserving the old representative rather than MIN(text). |
| Employee summary | SUM(Amount/Discount/Total) is explicit; printed username spelling comes from the minimum matching SalesID row. |
| Purchase-period/supplier and unposted pages | Their active queries are not arbitrary grouped rows. Unused purchaseItem helpers contained invalid ItemName-on-detail SQL and were removed rather than assigned invented behavior. |

Bill detail Rate values are printed per detail row, not selected arbitrarily from
a group. The existing catalogue-price multiplication in item summaries is
preserved; this slice does not change it into historical-rate accounting.

## Factory repair and intentional changes

The original factory query referred to `canteen_sales.Date` without joining that
table and generated a warning. The repaired query joins the sales parent and
uses its Date, as the original predicate explicitly requested. It does not add an
unrequested Post filter. The actual fixture contains no raw-material items, so
the repaired report remains visibly empty in both captured ranges: there is **no
manufactured expected text difference**. A targeted synthetic fixture below
proves the now-working nonempty case and date exclusion.

Other intentional changes are authentication, escaping, prepared SQL and removal
of PHP warnings/removed APIs. Normal fixture business text matches exactly.
No UI redesign, schema change, price-policy change or business write is added.
