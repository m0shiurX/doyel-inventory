# R5 — administrator restore, review and progress UI

Implemented `Restore.php`, `codes/restore.js`, `css/restore.css` and an admin-only
Accounts link. The page and JSON status endpoint require the existing admin
contract before reading jobs or database metadata. It displays the installed
application/build, recognized database engine token and canonical schema
compatibility, with separate restore-package and existing SQL downloads.

An owner-configured `restore_dir` is required. Missing configuration shows setup
instructions without attempting to create directories, read owner credentials,
start a helper or change database privileges. Actual `.doyel.gz` multipart uploads
use R3's private quarantine API; SQL receives a fixed owner-conversion message.
Missing/oversized POST bodies and incomplete uploads receive bounded messages.
CSRF and session-bound operation/job nonces protect all mutations. Upload nonce
replay resolves to the original receipt. No filename is persisted by the UI.

The review reads only fixed, validated job IDs and the bounded public validation
JSON. It escapes displayed values and selects specific fields; it never displays
raw rows, usernames, passwords/hashes, private paths, importer errors or arbitrary
JSON. It shows current/candidate counts, aggregate financial totals, date coverage,
role counts, source versions, backup age, UTC times and database identities.
Expected differences from an older snapshot are explained without calling them
corruption. The old database is retained; recent work is not merged automatically.

Activation requests require a visible HTML work-gap acknowledgement and explicit
confirmation. Activation, acceptance and pre-reopening rollback requests require
a fresh password match against the current admin ID and current database role.
The check uses SELECT plus `auth_password_matches`; it does not invoke login,
rehash passwords or create another database connection. Passwords are removed
from POST memory before recording fixed R3 action requests and never enter job
records, URLs, sessions or queries. The owner helper independently approves every
request and must verify candidate credentials offline before a switch. The page
cannot recover/reset accounts or claim a request completed the operation.

Polling uses one same-origin request at a time, every three seconds, and stops at
terminal states or unavailable/redirected service responses. It explains service
maintenance, durable jobs, saved URLs and fresh login after generation changes.

Verification on PHP 8.4.27 / MySQL 8.4.13:

- PHP lint passes for Restore, Accounts and the portable test; Node syntax check
  passes for polling. The runtime allowlist includes all three UI assets.
- `php tools/restore/ui-check.php < /absolute/private-owner-input.json` passes
  **32 isolated HTTP checks**. The STDIN object contains owner_user and
  owner_password; credentials never enter command arguments or output. The test
  creates a random canonical two-user database and a restricted runtime account
  with escaped exact database grants, builds the allowlisted release, runs a
  loopback PHP server on port 8166, then removes its own DB/account/private files.
  It never reads or modifies existing reference, production or credentials DBs.
- Real fresh admin/staff login and generation-aware cookies prove role guards;
  malformed IDs, missing POST, invalid CSRF and SQL uploads are refused. Actual
  multipart quarantine and upload/action nonce replay are exercised. Status is
  admin-only and exposes selected fields. Owner-published XSS is escaped and
  unrelated private fields are omitted. Backup age, inventory timestamp and
  comparison checks are present in the review.
- Wrong current-admin password returns 403 and creates no action. Correct current
  password records only the fixed activation request. Reauthentication leaves
  all password hashes byte-exact. During read-only acceptance uploads are refused,
  while fresh password checks record acceptance/rollback requests. An owner-only
  reset of the synthetic fixture admin to a legacy MD5 hash precedes a fresh
  acceptance login: that hash remains byte-exact, proving rehash suppression.
  All 13 table contents remain unchanged throughout acceptance, and no accounts
  are added or removed. Jobs, sessions and the HTTP log contain no plaintext
  test passwords. Frozen maintenance returns 503 for status polling.

The earlier exploratory HTTP checks used synthetic sessions and isolated package
bytes under the OS temporary directory. The committed reproducible test uses
fresh real logins and wholly disposable canonical data. No screenshots or client
rows are committed. An initial automatic approval review failed because its usage
limit prevented review; later reviewed PHP test runs succeeded. No rejected
operation was bypassed.

R4's published validation shape is integrated: schema.version/compatible,
comparison flags, customer-balance count/SHA256, aggregate financial/date/role
inventory, current counts and active_counts_asof. Missing/unverified flags block
activation requests. R6's maintenance mode permits only accept/rollback mutations
here during acceptance; uploads and new activation requests are refused.

Real Windows service ACLs, helper lifetime, browser reconnection after an actual
service stop and complete activation/acceptance remain integration/target gates.
The UI does not start the helper or perform a switch, rollback or business write.
